ГЕНЕРАТОР СТРАХОВЫХ ИСТОРИЙ — ПЛАН ПРОЕКТА
==========================================

С чего начать: сначала определить, что приложение должно выдавать.
От этого зависит всё остальное, код лучше писать после этого.


1. ОПРЕДЕЛИТЬ НАЗНАЧЕНИЕ И РЕЗУЛЬТАТ
------------------------------------
"Страховая история" может означать разное:
  - Синтетические данные: правдоподобная история полиса и убытков
    для тестирования, обучения моделей или демо.
  - Сценарный анализ: "что может случиться с этим объектом и сколько
    это будет стоить" (андеррайтинг, расчёт тарифа).
  - Оценка конкретного убытка: прогноз выплаты по описанному событию.

Если результат выглядит как настоящие документы, сразу помечать его как
сгенерированный (например, водяным знаком). Иначе им могут злоупотребить
для подачи фиктивных заявлений о страховом случае. Заложить в дизайн
с самого начала.


2. МОДЕЛЬ ДАННЫХ
----------------
  Объект:   тип, марка/модель, год, цена покупки, состояние, регион
  Полис:    вид (КАСКО, ОСАГО, гаджет), франшиза, лимит, срок
  Событие:  тип (кража, повреждение, ДТП, залив), дата, степень ущерба
  Выплата:  сумма, учёт износа, франшиза, обоснование


3. ДВА НЕЗАВИСИМЫХ БЛОКА ЛОГИКИ
-------------------------------
  Расчёт компенсации
    Как: детерминированные правила — рыночная стоимость минус износ
         по возрасту и состоянию, умножить на коэффициент ущерба,
         вычесть франшизу, ограничить лимитом.
    Почему: каждую цифру можно объяснить и проверить.

  Текст истории
    Как: LLM (например, Claude API) генерирует описание
         по структурированным данным.
    Почему: языковая модель хорошо пишет текст, но с цифрами ошибается,
            поэтому суммы считает код.

Машинное обучение для прогноза подключать позже, когда появятся реальные
данные о выплатах. До этого достаточно правил.


4. MVP НА ОДНОМ ТИПЕ ОБЪЕКТА
----------------------------
Начать со смартфонов: простая амортизация, понятные риски (разбит экран,
кража, залитие), легко найти рыночные цены.
Автомобили значительно сложнее (ОСАГО/КАСКО, калькуляция ремонта, УТС) —
вторым этапом.


5. СТЕК
-------
  Frontend: React/Next.js (на старте — простая HTML-страница без сборки)
  Backend:  Python (FastAPI) — удобно для расчётов и будущего ML
  БД:       SQLite на старте, позже PostgreSQL
  LLM:      Claude API для текста истории, структурированный вывод (JSON)


ПОРЯДОК РАБОТЫ
--------------
  1. Записать формулы расчёта для смартфонов и проверить на 5-10 примерах.
  2. Написать функцию расчёта на бэкенде и тесты к ней.
  3. Сделать простую форму, которая показывает расчёт.
  4. Подключить генерацию текста истории.
  5. Добавлять новые типы объектов и улучшать модель.
